# Lesson 03.5 — Language builders: Go, Rust, Python

**You will:** package one small program each with `buildGoModule`,
`rustPlatform.buildRustPackage` and `python3Packages.buildPythonApplication`, and see how
each builder handles the language's own dependency manager.

## Why language builders exist

Every modern language has a package manager that wants to download dependencies during
the build: `go mod download`, `cargo fetch`, `pip install`. The Nix sandbox has no network.
Each builder solves this in one of two ways:

1. **One fixed-output derivation for all dependencies.** The builder runs the language's
   own fetcher in a FOD, so it may use the network, and you give the hash of the result:
   `vendorHash` (Go), `cargoHash` (Rust). Simple, but one opaque hash for everything.
2. **Dependencies as Nix packages.** Each dependency is its own derivation. Rust can do
   this from `Cargo.lock` (`cargoLock.lockFile`), because the lock file already contains a
   checksum per crate. Python in nixpkgs works this way entirely: dependencies come from
   `python3Packages`, built by Nix, never from PyPI at build time.

Each builder is `mkDerivation` underneath, with language-specific phases and hooks. They
accept `finalAttrs` and `__structuredAttrs`, and turn on `strictDeps` themselves
(*The Standard Environment*, `strictDeps`). Sources: Nixpkgs manual,
`doc/languages-frameworks/go.section.md`, `rust.section.md`, `python.section.md`.

## Go: `buildGoModule`

```text file=go/go.mod
module example.com/hello-go

go 1.22
```

```go file=go/main.go
package main

import (
	"fmt"
	"os"
)

// Set at link time: -X main.version=...
var version = "dev"

func greeting(name string) string { return "Hello, " + name + "!" }

func main() {
	if len(os.Args) > 1 && os.Args[1] == "--version" {
		fmt.Println("hello-go", version)
		return
	}
	fmt.Println(greeting("Go"))
}
```

```nix file=go.nix
{ lib, buildGoModule }:

buildGoModule (finalAttrs: {
  pname = "hello-go";
  version = "1.0.0";
  src = ./go;

  __structuredAttrs = true;

  # No dependencies, nothing to vendor: no goModules derivation at all.
  vendorHash = null;

  # Inject the version, so the binary cannot disagree with the package.
  ldflags = [
    "-s"
    "-X main.version=${finalAttrs.version}"
  ];

  meta = {
    description = "Greets from Go";
    license = lib.licenses.mit;
    mainProgram = "hello-go";
  };
})
```

What `buildGoModule` does (`pkgs/build-support/go/module.nix`):

- With a `vendorHash`, it first builds `goModules`: a FOD that runs `go mod vendor`. Its
  hash is the `vendorHash`. The main build copies that in as `vendor/` and builds with
  `-mod=vendor` and `GOPROXY=off` — no network.
- With `vendorHash = null`, it uses the `vendor/` directory in the source, or none at all.
- It builds every `main` package (or only `subPackages`) with `go install`, adds
  `-trimpath` and an empty `-buildid` for reproducibility, and runs `go test` in the check
  phase.

To get a real `vendorHash`, use the fake-hash workflow from lesson 2:
`vendorHash = lib.fakeHash;`, build, copy the `got:` value.

## Rust: `buildRustPackage`

```toml file=rust/Cargo.toml
[package]
name = "hello-rust"
version = "1.0.0"
edition = "2021"
```

A `Cargo.lock` for a crate without dependencies lists only the crate itself. This is
exactly what `cargo generate-lockfile` writes:

```toml file=rust/Cargo.lock
# This file is automatically @generated by Cargo.
# It is not intended for manual editing.
version = 4

[[package]]
name = "hello-rust"
version = "1.0.0"
```

```rust file=rust/src/main.rs
fn main() {
    match std::env::args().nth(1).as_deref() {
        Some("--version") => println!("hello-rust {}", env!("CARGO_PKG_VERSION")),
        _ => println!("Hello, Rust!"),
    }
}
```

```nix file=rust.nix
{ lib, rustPlatform }:

rustPlatform.buildRustPackage (finalAttrs: {
  pname = "hello-rust";
  version = "1.0.0";
  src = ./rust;

  __structuredAttrs = true;

  # Vendor the crates listed in Cargo.lock, using its per-crate checksums.
  # The alternative is `cargoHash = "sha256-…";` (one FOD running `cargo vendor`).
  cargoLock.lockFile = ./rust/Cargo.lock;

  meta = {
    description = "Greets from Rust";
    license = lib.licenses.mit;
    mainProgram = "hello-rust";
  };
})
```

The version printed comes from `Cargo.toml` (`CARGO_PKG_VERSION`), not from Nix. If the
two disagree, nothing in the build notices — project 03c adds a test that does.

## Python: `buildPythonApplication`

```toml file=python/pyproject.toml
[build-system]
requires = ["setuptools"]
build-backend = "setuptools.build_meta"

[project]
name = "hello-py"
version = "1.0.0"

[project.scripts]
hello-py = "hello_py:main"

[tool.setuptools]
py-modules = ["hello_py"]
```

```python file=python/hello_py.py
import sys
from importlib.metadata import version


def main():
    if sys.argv[1:] == ["--version"]:
        print("hello-py", version("hello-py"))
    else:
        print("Hello, Python!")
```

```nix file=python.nix
{ lib, python3Packages }:

python3Packages.buildPythonApplication (finalAttrs: {
  pname = "hello-py";
  version = "1.0.0";
  src = ./python;

  __structuredAttrs = true;

  # Build with the PEP 517 backend named in pyproject.toml.
  pyproject = true;
  # [build-system] requires — Python packages needed to *build* the wheel.
  build-system = [ python3Packages.setuptools ];
  # [project] dependencies would go in `dependencies = [ … ];` (none here).

  # After installing, check that the module imports.
  pythonImportsCheck = [ "hello_py" ];

  meta = {
    description = "Greets from Python";
    license = lib.licenses.mit;
    mainProgram = "hello-py";
  };
})
```

`buildPythonApplication` builds a wheel with `pypa/build` (no isolation, no network),
installs it, and wraps the console scripts so they find their dependencies. Applications
go in `pkgs/by-name` and take `python3Packages` as an argument; libraries live in
`python3Packages` itself (manual, *Python*, `buildPythonApplication` function).

## Build all three

```nix file=default.nix
let
  pkgs = import ./nixpkgs.nix {
    config = { };
    overlays = [ ];
  };
in
{
  go = pkgs.callPackage ./go.nix { };
  rust = pkgs.callPackage ./rust.nix { };
  python = pkgs.callPackage ./python.nix { };
}
```

The toolchains come from the binary cache; only your three programs are compiled.

```bash timeout=3600
nix-build -A go -o result-go
nix-build -A rust -o result-rust
nix-build -A python -o result-python
for p in go rust python; do
  exe=$(nix eval --raw --file default.nix "$p.meta.mainProgram")
  ./result-$p/bin/$exe
  ./result-$p/bin/$exe --version
done
```

```text expect
Hello, Go!
hello-go 1.0.0
Hello, Rust!
hello-rust 1.0.0
Hello, Python!
hello-py 1.0.0
```

## Look behind the builders

The dependency handling is visible as attributes of each package:

```bash
echo "go vendorHash: $(nix eval --json --file default.nix go.vendorHash)"
nix-build -A rust.cargoDeps -o cargo-deps
ls -A cargo-deps
head -n 1 result-python/bin/hello-py
```

```text expect
go vendorHash: null
Cargo.lock
.cargo
/nix/store/
```

- Go: `vendorHash = null`, so there is no dependency derivation.
- Rust: `cargoDeps` is a directory with the lock file, a cargo config that redirects
  crates.io to the vendored copies, and one symlink per crate (none here).
- Python: `bin/hello-py` is a wrapper whose `#!` line points into the store; it runs the
  real script (`.hello-py-wrapped`) with the interpreter and module search path fixed.

Compare the runtime closures. A Go program that uses no C code links statically and needs
almost nothing; Python brings its interpreter:

```bash
for p in go rust python; do
  echo "$p: $(nix-store --query --requisites "$(readlink result-$p)" | wc -l) store paths"
done
```

## Exercise: tests gate the build

`buildGoModule` runs `go test` in its check phase. Add `go/main_test.go` with a test for
`greeting`. First write it wrong and watch the build fail; then fix it.

<details><summary>Solution</summary>

A failing test first:

```go file=go/main_test.go
package main

import "testing"

func TestGreeting(t *testing.T) {
	if got := greeting("Nix"); got != "Hullo, Nix!" {
		t.Fatalf("greeting(\"Nix\") = %q", got)
	}
}
```

```bash fails
nix-build -A go -o result-go
```

```text expect
FAIL
```

The package is never produced: a failing check phase fails the derivation. Fix the
expectation:

```go file=go/main_test.go
package main

import "testing"

func TestGreeting(t *testing.T) {
	if got := greeting("Nix"); got != "Hello, Nix!" {
		t.Fatalf("greeting(\"Nix\") = %q", got)
	}
}
```

```bash
nix-build -A go -o result-go
./result-go/bin/hello-go
```

```text expect
Hello, Go!
```

The test file changes the source, so the output path changes too — even though the binary
is the same. (`lib.fileset` could exclude `*_test.go` from a separate, test-free source; in
practice nixpkgs keeps tests in the source and runs them.)

</details>

## Check yourself

<details><summary>Why does <code>buildGoModule</code> need a <code>vendorHash</code> but <code>buildPythonApplication</code> has no equivalent?</summary>

Go dependencies are fetched by `go mod vendor` inside a fixed-output derivation, whose
output needs a hash. Python dependencies in nixpkgs are ordinary Nix packages from
`python3Packages`, each built (and hashed) by Nix itself; nothing is downloaded during the
application's build.

</details>

<details><summary>What is the advantage of <code>cargoLock.lockFile</code> over <code>cargoHash</code>?</summary>

No extra hash to maintain: the lock file already contains a checksum for every crate, so
Nix makes one small fetch derivation per crate. Crates shared between packages are fetched
once. The cost is keeping a copy of `Cargo.lock` next to the package when upstream does not
ship one. `cargoHash` is one opaque hash over the whole vendor directory.

</details>

<details><summary>The Rust program prints the version from <code>Cargo.toml</code>, the Go program the one from Nix. Which is better?</summary>

Neither alone. Taking it from Nix (Go's `-X`) means the binary always matches the package
attribute; taking it from the source means it always matches upstream. Either way, add a
version test (`versionCheckHook` or `testers.testVersion`) so a mismatch fails loudly —
that is project 03c.

</details>
